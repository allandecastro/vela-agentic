# Project files

This page lists the files the pack reads and writes in a Vela project, what each one holds and who may change it.
It is for developers and reviewers who work in a project an agent has built. The templates are in
[`references/build-report-template.md`](https://github.com/allandecastro/vela-agentic/blob/v0.6.0/references/build-report-template.md).

| Path | Written by | Committed | Holds |
| --- | --- | --- | --- |
| `PROJECT.md` | `vela init`, once | Yes | The publisher prefix and each package's solution. |
| `docs/features/<slug>/README.md` | The agent, per story | Yes | The Vela Canvas, grown into the Build Report. |
| `docs/rules/<table>.md` | The agent with the human, at design | Yes | The business rules of a table and their cases. |
| `docs/adr/NNNN-<title>.md` | The agent with the human, at design | Yes | One architecture decision per file. |
| `.vela-runs/<slug>/` | The agent, during the run | No | The run trace, the review output and `plan.json`. |

## `PROJECT.md`

`vela init` writes `PROJECT.md` once, with the publisher prefix and a map from each package to its target
solution. The CLI never reads it. The agent reads it and passes the values as flags, for example
`vela plan --solution <uniquename>`, and never copies them into other files. For a new project the agent reads the
prefix with `vela solution show <uniquename> --json` (read-only). See [Scaffold a solution](../guides/scaffold.md).

## `docs/features/<slug>/README.md`

One folder per story. The file starts as the Vela Canvas (`kind: canvas`), committed before any code, and becomes
the Build Report (`kind: feature`) at the apply gate. It is the pull request body. A new story on an existing plugin
gets its own slug. See [The build loop](build-loop.md).

## `docs/rules/<table>.md`

The rules registry: the business rules triggered on a table, each in Given / When / Then / Otherwise, with numbered
cases (`ACC-002/C1`), the affected tables, and trace lines to the handler and the test class. Each test carries its
case id as a `Case` trait.

- A rule on the base branch is in force; there is no status field. A rule on a branch is proposed, and merging the
  pull request approves it.
- A retired rule is deleted with its tests. Git keeps the history.
- The agent writes rules only in the design phase, asking the human what only they can decide.

## `docs/adr/NNNN-<title>.md`

Architecture decisions that outlive a story and are costly to reverse: the security context plugins run in, an
external provider and its failure policy, a caching strategy, plugin versus Custom API versus flow. One decision per
file, with [MADR](https://adr.github.io/madr/) front matter without a status, plus its scope (`applies-to`, `tables`,
`areas`). The agent reads the ADRs that touch a story before planning and never asks again what one answers. A
business rule, a choice local to one story or a machine value such as the publisher prefix is not an ADR.

## `.vela-runs/<slug>/`

The working material of a run, kept out of git (the agent adds `/.vela-runs/` to `.gitignore`):

- `trace.md`: one row per step with the command, its real exit code and the verdict.
- `review.md`: the reviewer's output, verbatim, one section per round.
- `plan.json`: the `vela plan --out` output.

The agent pastes the trace and the review into the pull request. The trace is also the input for
[vela-debug-plugin](skills/vela-debug-plugin.md) and for resuming an interrupted story.

## Files the agent never edits

- Generated files: `Models/Generated/`, `*.g.cs`, `*.generated.cs`, and any file marked `<auto-generated`. The agent
  regenerates them with `vela models`. See [Early-bound models](../guides/models.md).
- `docs/rules/` during the build, apart from the trace lines and recorded amendments.
- The `AGENTS.md` that `vela init` writes is context for the agent; where it differs from the pack, the pack wins.
