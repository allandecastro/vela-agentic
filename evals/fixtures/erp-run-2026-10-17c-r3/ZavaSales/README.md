# ZavaSales

Dataverse plugin solution generated by `vela init`. It builds on
`Vela.Plugins` (v0.36.0) and is ready to register with `vela`.

This is a minimal scaffold: the projects ship no sample code, waiting for yours. Run `vela init --samples` in
another folder to see worked examples of every pattern.

## Projects

- `src/Zava.Shared` - early-bound entity models and shared services, referenced by the plugin project. Empty until you run `vela models`.
- `src/Zava.Plugins` - your plugin package. Builds a Dataverse plugin-package `.nupkg` (not a bare `.dll`). Empty until you add a plugin.
- `src/Zava.Integrations` - a second plugin package, same mechanics as Plugins. Empty until you add a plugin (`--project src/Zava.Integrations`).
- `tests/Zava.Plugins.Tests` - unit tests with `Vela.Testing` (no Dataverse connection). Empty until you run `vela add test`.
- `tests/Zava.Integrations.Tests` - unit tests for the Integrations package. Empty until you run `vela add test`.

> **Restore source:** the projects reference `Vela.Plugins` / `Vela.Testing` from **nuget.org** (the default package source), so a plain `dotnet restore`/`build` works with no extra configuration.

## Next steps

Run these from the solution root:

1. Generate early-bound models from your environment: `vela models --entities account,contact --project src/Zava.Shared/Zava.Shared.csproj --interactive` (it writes into the project's `Models/Generated` folder, in the `Zava.Shared.Models.Generated` namespace).
2. Add a plugin or Custom API (`--entity` is the early-bound model type): `vela add plugin MyPlugin --entity Account --filtering-attributes Name --project src/Zava.Plugins` (a Create/Update step needs its filtering columns) or `vela add customapi MyApi --global --project src/Zava.Plugins`.
3. Build: `dotnet build ZavaSales.sln -c Release`.
4. Test it: `vela add test MyPlugin --entity Account --project tests/Zava.Plugins.Tests`, then `dotnet test tests/Zava.Plugins.Tests -c Release`.
5. Preview and deploy into your Dataverse solution: `vela plan --packages-dir artifacts --solution ZavaSales`, then `vela apply --packages-dir artifacts --solution ZavaSales` (use your solution's unique name; `--solution` gives the package its publisher prefix, without which `vela plan` refuses an unprefixed package).

Until you add a plugin, the package registers nothing - `vela plan --packages-dir artifacts --solution ZavaSales` simply reports no changes.

`vela add customapi` names a Custom API `zava_<Name>`: the publisher prefix recorded in the projects (`VelaPublisherPrefix`).

## Signing the plugin package

The build does **not** sign the assembly. If the `Zava.Integrations` plugin uses a **managed identity**
(and therefore needs publisher identity + tamper-evidence on the package), re-scaffold with
`vela init <name> --managed-identity --force` to add an opt-in, CI-gated signing step to the Integrations build, or
sign a packed `.nupkg` yourself:

```powershell
vela sign --package artifacts/Zava.Integrations.1.0.0.nupkg --fingerprint <fingerprint>
```

`vela init --force` regenerates the scaffold in place. It only overwrites or removes the files it generated that
you have not edited since (it records them in `.vela/scaffold-manifest.json`; commit that file); your own files
and edited ones are kept.
