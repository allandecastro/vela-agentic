## Findings against the skills
None of these block the run.

1. **minor** - `skills/vela-apply/references/build-report-template.md:164`, Gate line: "`vela apply -p <pkg> --solution <uniquename> -i`". That command uses an interactive login and does not name the environment the plan previewed. This contradicts `skills/vela-apply/SKILL.md` step 9 ("`vela apply -p <pkg> --solution <uniquename> <connection>` - the same package ..., the same `--solution`"), which implies the same connection. With `-i` the target is whatever URL vela remembered, so it is not pinned to `--url` in `plan_command`. The actor copied the template: it wrote `-i (or --url <org>)` with a placeholder, even though its plan used `--url https://<dev-org>.crm.dynamics.com`. The template should carry the plan's connection (`<connection>` = the same `--url ...` that was previewed), so the gate applies to the org that was planned.
2. minor (coverage gap, carried over from 2026-10-02 and 2026-10-04): the `managed-rank-collision` gotcha was again not exercised. The dev org emits no rank-collision diagnostic for PreOperation Create/Update on account. Either the scenario needs a trigger that collides, or the gotcha should come out of `gotchas_exercised`.
3. minor (optional step, carried over): `vela models --verify` was not run after generation. If the scenario wants that evidence, `skills/vela-models/SKILL.md` should make it the default follow-up.

Scenario-wording note (evaluator side, not a pack defect): the scenario says assembly-not-found appears as a "diagnostic". In vela 0.25.0 it is an `info` line with `diagnostics: []`, and `skills/vela-apply/SKILL.md` step 6 already says so. The actor read it correctly.
