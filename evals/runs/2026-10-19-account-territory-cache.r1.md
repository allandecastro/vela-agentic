## Findings against the skills
No blocker.

1. **minor** - `skills/vela-plan-review/references/plugin-authoring-api.md:245` says the cache TTL means "a change shows only after it". It says nothing about a cached **id** that points at a row deleted inside the TTL.
   - What happened: the actor's first implementation cached name→id and would write a lookup to a deleted territory, which fails the save on a live org. Only the isolated reviewer's round 1 caught it (`logs/review-round1.md`, Required R1). The fix costs one by-id SYSTEM read per matched save, partly undoing the cache.
   - The harness `Seed` does not validate lookups, so no test caught it before review.
   - Suggested: one clause in the caching line (or `dataverse-gotchas.md`): "a cached id can outlive its row; decide (and record) whether a deleted row may fail the save until the TTL ends, or confirm it before writing".
2. **minor** - `skills/vela-plan-review/references/plugin-authoring-api.md:117` names `ctx.HasChanged<Account>(e => e.Name)` as the "changed" test (the round-1 reviewer called it the Vela idiom), but the actor hand-rolled an Ordinal compare (`AccountSalesTerritory.cs:46`), so a case-only edit re-sets the territory although the match is case-insensitive. The pack does not say how "changed" relates to the comparison the rule uses. Left as a gate question by the actor; not a failed criterion.

3. **minor** - `skills/vela-code-review/references/review-checklist.md:101-102` says "behaviour that depends on rights with no `WithSecurity` test - **Required**". It does not say whether a recorded SYSTEM elevation (here, the reason the shared cache is safe) needs a test that pins it.
   - What happened: no test proves the SYSTEM read. The round-2 reviewer passed the build without one. The planted-(a) reviewer then flagged the same gap: a `SystemService` → `Service` regression stays 24/24 green.
   - The previous run of this scenario (2026-10-18f) had such a test (C14), so whether the test exists depends on the actor, not on the pack.
   - Suggested: one line in vela-test-harness or the checklist: "an elevation the Canvas relies on (e.g. SYSTEM for a shared cache) gets a `WithSecurity` test where a caller without read rights still gets the result".
